## Recovery method

The delivery trail was reconstructed from the sealed source-v2 carrier, earlier recovery archives, local Git bundles, Linear records, GitHub history, and the live organization state.

Publication followed these rules:

1. validate source archives and reject credential-like content;
2. publish governance and contracts before dependent implementations;
3. preserve exact approved source history where possible;
4. semantically reconcile newer live work rather than force-pushing it away;
5. rename the recovered Flutter repository to `mbk-flutter` while preserving repository identity and Git objects;
6. publish the monorepo only after every referenced child commit was reachable; and
7. rerun the publisher to prove idempotency.

If a canonical name had been occupied by an unrelated repository with no shared lineage, the approved fallback was `<name>-2`. No such conflict was found. Occupied canonical targets either came from the recovery publication itself or contained the same recovered product source with newer reviewed additions.
